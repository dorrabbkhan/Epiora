# v0.3 Task 16 — performance and size measurement

**Status:** `import_1m` fails in the measurement environment — 10 of 10
samples ended in `RpcError: SQLITE_IOERR` (sqlite3 result code 10). All other
scenarios and both size sets measured cleanly.

## Headline: no successful 1,000,000-row sample exists

The measurement run (10 samples, 1,000,000 rows) failed at `import_1m` in
every sample while the store wrote to OPFS. `reimport_1m`, `open_tables_1m`
and `grid_scroll_1m` were recorded as skipped-with-reason on every sample, so
**there is no successful 1M sample on which to base `import_1m` /
`open_tables_1m` threshold proposals.** The failure is diagnosed below: it is
an environment ceiling of Chromium's off-the-record profile (~0.85–1.06 GiB
of OPFS usage), not the reported origin quota and not a product-imposed
limit.

## Diagnosis of the `SQLITE_IOERR`

Every 1M sample failed identically: `commitImport` wrote to OPFS through the
`opfs-sahpool` VFS until total OPFS usage reached ~0.85–1.06 GiB, then a
`FileSystemSyncAccessHandle.write()` returned a short write, which
`xWrite` reports as `Error: Unknown write() failure.` and SQLite maps to
`SQLITE_IOERR` (result code 10). Evidence, all from the run above and the
probes:

- **Worker console** (captured per failure): `opfs-sahpool: Error: Unknown
  write() failure.` inside `xWrite`, followed by
  `sqlite3_step() rc= 10 SQLITE_IOERR SQL = INSERT INTO records …`. A short
  write — not an exception — means the browser refused to extend the file.
- **Failure usage vs quota:** failures occurred at `usageBytes`
  876,886,586–1,064,000,842 against `quotaBytes` ~11.6–11.8 GB — under 10 %
  of the reported origin quota, so quota is not the cause.
- **OPFS walk at failure:** the pool file decoded as `/epiora` had grown to
  872,886,272–1,060,000,522 bytes; `/epiora-journal` stayed at 106,496 bytes;
  the rest of the pool is ~63 unused 4 KiB slot files. Writes fail while the
  database file is being extended, mid-transaction
  (`progress="write 720000/1000000"` … `"write 870000/1000000"`).
- **Host disk and memory are not the cause** (probe 43013081306, rows=800k):
  `df -h` shows `/dev/root` 145 GiB with **82 GiB free** and `free -h` shows
  **14 GiB available** both before and after the spec.
- **Failure-point reproducibility:** the write ceiling varies per fresh
  browser context (0.83–1.01 GiB observed across the ten 1M samples and the
  probes). Playwright launches an off-the-record (ephemeral) profile;
  Chromium caps OPFS growth in such profiles far below the reported quota.
  This is a measurement-environment ceiling, consistent with the sqlite
  project's documentation that sahpool maps any underlying OPFS write
  failure to `SQLITE_IOERR`.
- **Smallest failing row count** (import alone, one context each):

  | rows | `import` | `reimport` | `open_tables` | `grid_scroll_<rows>` |

  at ≥500,000 because the write journal adds roughly one database-size of

  boundary is a band, not a single count.

## Follow-ups noticed

- **Off-the-record OPFS write ceiling (~0.85–1.06 GiB).** The 1M-row import
  cannot complete in a Playwright ephemeral profile. Task 17's 1M gate needs
  either a persistent browser context, a different quota profile, or a
  product change (e.g. chunked import commits) — none of which is Task 16's
  scope. Real users in Chromium incognito windows would hit the same wall;
  whether persistent-profile Chromium (and Firefox/WebKit) shares it is
  unknown — worth a dedicated probe before the product commits to 1M-row
  imports.
- **`grid_scroll_<rows>` breaks at ≥250,000 rows — product bug.** The data
  grid enters an infinite update recursion (`Minified React error #520`,
  then `RangeError: Maximum call stack size exceeded` in
  `getRows → commit → updateCollection → getCollection`, TanStack
  collection path): at 250k the spec hit the 30-minute test timeout with the
  page wedged; at 500k–700k the page crashed outright. Not an OPFS issue and
  not a threshold issue.
- **`reimport_<label>` hits the OPFS ceiling earlier than `import`** because
  the journal roughly doubles peak usage (~862–904 MB at ≥500k).
- **`grid_scroll_10k` is slow in absolute terms** (median 157,130.8 ms,
  frameP95 p90 689 ms for 1,509 scroll steps) — the scroll workload itself,
  not a failure.
