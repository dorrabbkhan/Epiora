# Epiora v1.1 Epi Info Projects and Data Management Implementation Plan

> **Execution:** run by the Epiora conductor (Claude Code, `CLAUDE.md`) delegating each task to a fresh local Devin session and a fresh review session (`scripts/conductor/build-prompt.sh … | scripts/conductor/devin.sh …`). One task per branch, named `v1.1/task-<N>-<short-name>`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v1.1 as a pre-release: Epi Info 7 (Access, SQLite, SQL Server on desktop) and Epi Info 3.5.x projects open as Epiora projects with labels, links, programs and check code; Access and SQLite projects can be refreshed by re-import; SELECT, SORT, RECODE, DEFINE, ASSIGN, MERGE, RELATE and the rest of §5.3 run as a replayable recipe with receipt v4; a program editor runs `.pgm` scripts and reports every unsupported command; a migration report compares results with Epi Info 7 and, optionally, the user's own saved output; a command register maps every Epi Info 7 feature to a version ≤ v1.6.

**Architecture:** Every legacy source is read into one binary table-batch format (`EPTB`): the mdbtools wasm module and sqlite-wasm encode it in the worker, `tiberius` encodes it in the Tauri backend. A new Rust crate `epiora-legacy` decodes batches and maps Epi Info 7 and 3.5.x layouts into Epiora datasets (extended with Time, DateTime, labels and links), shipped as a lazily loaded `epiora-legacy-wasm`. A new crate `epiora-lang` holds the expression language, cleaning commands, recipes and the `.pgm` parser and planner, shipped as a lazily loaded `epiora-lang-wasm`. The planner turns a program into actions; the worker runs cleaning actions in lang-wasm (which returns the working-view snapshot and hash) and procedures in the unchanged core-wasm, with a working-view stamp in `RunContext` producing receipt v4.

**Tech Stack:** as v1.0, plus mdbtools 1.0.1 `libmdb` (LGPL-2.1, Emscripten build; native build for tests only), `tiberius` (Tauri backend only), `rusqlite` (dev/test and golden tooling only), the SQL Server Developer edition container (CI only). All at the latest release at task time, pinned in lockfiles.

**Spec:** `docs/superpowers/specs/2026-11-22-epiora-v1.1-epi-info-projects-design.md` (all sections), with the v1.0 spec §3.2, §7.3, §8, the v0.3 spec §4–§6, §8, the spike reports `docs/spikes/mdb-wasm.md` and `docs/spikes/ei7-windows.md`, and the platform spec §7.4, §12.

## Global Constraints

- Every v0.2–v1.0 rule stands: `libm`-only float maths in Rust engine crates (clippy `disallowed-methods`); no clock, environment or locale reads in Rust; `unwrap`/`expect`/`panic` denied outside tests; every failure a typed error with a stable `code()`; `Estimate::Value | Undefined { reason }`, never NaN; the main thread never touches wasm or SQLite; timestamps and as-of dates only from a worker.
- Tolerance classes unchanged: `closed_form` 1e-9, `iterative` 1e-6, `ei7_display` and `openepi_display` = `0.5 × 10^−d`. A disagreement with Epi Info 7 beyond display precision is an owner escalation, never a tolerance change.
- Receipts v1, v2 and v3 stay byte-for-byte unchanged (goldens in `crates/epiora-core/tests/golden/`). Receipt v4 appears only when a run is on a working view with at least one recipe step.
- Dataset hashes of datasets without labels, links or the new types are unchanged (every existing fixture and golden receipt keeps its hash).
- Fixtures are produced only by `fixtures/generate.R`, the `ei7.yml` workflow, the `openepi.yml` workflow and the new `legacy-golden.yml` workflow; never hand-edited; never in a PR that touches `crates/`, `app/` or `spikes/` (fixture guard). v1.1 fixture tasks: 2, 3 and 4.
- mdbtools ships only as the separate wasm module `app/public/mdb/` (browser and desktop webview); the native build is for tests and golden tooling and is never in a release artifact. Its LGPL notice and source offer ship next to the module.
- SQL Server credentials and connection strings live only in memory for one import: never in the store, settings, logs, error messages, receipts or the migration report.
- Budgets: core engine wasm ≤ 409,600 bytes `gzip -9` (unchanged); first load < 5,000,000 bytes; `import_1m` ≤ 89,550 ms, `open_tables_1m` ≤ 2,874 ms, import-wasm ≤ 573,616 bytes, `means_1m` ≤ 3,173 ms unchanged. `epiora-lang-wasm`, `epiora-legacy-wasm` and the mdb module are reported until Task 18; their budgets and `legacy_import_large` only from the owner's pick at Task 18. No task invents a threshold.
- Licence AGPL-3.0-only on product code; `cargo deny check` clean; npm production dependencies pass the `--onlyAllow` list (LGPL-2.1 allowed only for the mdb module, recorded in `deny.toml`/licence config with a comment). Epi Info 7 code only with its Apache-2.0 notice (D2); its grammar is a reference, not compiled in.
- UI: only the Epiora component set; tokens only; zero axe violations in Chromium, Firefox, WebKit, light and dark; 320px and 200% zoom; strings in `app/src/ui/strings.ts` (legacy copy in `app/src/legacy/strings.ts`).
- No skipped tests; no number in a test, budget, fixture or decision rule changes without an owner escalation. Files under ~400 lines (new code in new files).
- Files outside a task's Files block are recorded in `docs/decisions.md` in the same PR.

**Task sizing:** a UI task whose Files block spans more than ~12 files, or that pairs a new component tree with a new e2e spec in three engines, is split by the author into (a) logic + unit tests and (b) UI + e2e; the conductor may propose the split to the owner before starting.

## Review Focus

1. **Text in an old Access 97 (JET3) file stored in a Windows code page** (French accents, Portuguese, Cyrillic): expect correct UTF-8 in the dataset, or a report entry naming the field and the code page assumed, never silent mojibake. → Task 5 `jet3_cp1252_text_decodes`, Task 7 `undecodable_text_is_reported`.
2. **An Access file that is not an Epi Info project** (any `.mdb` with ordinary tables): expect `legacy_layout_unknown` and an offer to import its tables as plain datasets, not a crash or an empty project. → Task 7 `plain_access_db_is_layout_unknown_with_tables`, Task 15 `plain_mdb_offers_table_import`.
3. **Access date-times**: Epi Info stores Date fields as Access DateTime (epoch 1899-12-30, possible time part, years before 1900): expect Date fields to keep the calendar date, Time and DateTime fields their time, and dates before 1970 or 1900 to round-trip. → Task 7 `access_datetime_epoch_and_time_split`.
4. **A `.pgm` saved by Epi Info 3.5 or edited in Notepad**: CRLF line endings, Windows-1252 text, mixed-case keywords, `*` and `//` comments, bracketed names with spaces: expect it to parse, or a `pgm_syntax` error with the right line, never a panic. → Task 12 `crlf_cp1252_mixed_case_program_parses`, `ei3_style_program_parses_or_reports`.
5. **Re-import while a working view is open on the old version**: expect the session to stay on its source version, a banner offering to move it to the new version (replaying its recipe), and no change to existing receipts. → Task 15 `reimport_keeps_open_session_on_old_version`.

- Hash rule (owner review): canonical bytes v1 unchanged; when any column uses Time/DateTime or any `label_set` is set, a trailing section `LBLS` (label sets in id order, each entry as value canonical bytes + UTF-8 label) is appended after the v1 bytes.
