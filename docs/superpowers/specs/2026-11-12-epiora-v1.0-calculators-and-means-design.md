**Status:** draft for owner review · **Date:** 2026-11-12 · **Owner:** Dorrabb

**Inputs:** [v0.2 engine core](2026-10-30-epiora-v0.2-engine-core-design.md),

This spec turns the first half of the roadmap's v1.0 line into a buildable design. The owner split the old
v1.0 in two (G2): this version ships every OpenEpi and Epi Info StatCalc calculator plus Classic Analysis
MEANS; regression and data management become v1.1. The refinements to the platform spec are listed in §14
and applied by the closing task (owner gate).

---

## 1. Intent

**Why.** The owner's goal is for Epiora to become the de facto tool for everything people use Epi Info and
OpenEpi for today, in classrooms and in the field. OpenEpi users need only calculators: no data, no forms, no
projects. Epiora can cover all of that in one version on the engine it already has, so v1.0 makes Epiora
something an OpenEpi user can switch to completely on the day it ships, and gives Epi Info users the first
Classic Analysis command beyond FREQ and TABLES. Epi Info desktop parity follows step by step (v1.1–v1.6, §14).

**Outcome.** A pre-release (G5) of the web app and desktop app in which:
- every calculator in OpenEpi and in Epi Info 7 StatCalc opens straight from a link, with no project, works
  offline, and matches R at its tolerance classes and OpenEpi at its displayed precision (Epi Info 7 StatCalc is
  a method source, not a numeric reference: it has no scriptable route, §5.2);
- MEANS runs on imported datasets in the Analysis workspace and matches Epi Info 7 and R;
- every result has an explain mode (plain language, plus the formula with the run's own numbers);
- every dataset result can be exported as an R script that reproduces it, and CI proves it does;
- every Analysis result card shows the equivalent Epi Info command.

**Who it is for.** OpenEpi users (students, instructors, analysts, field epidemiologists who use calculators
in the field); Epi Info users who analyse CSV/Excel data; v1.1 onwards, which builds on the explain and export
machinery defined here.

**Success criteria.**
1. Every calculator in the inventory (Task 1, owner-reviewed) exists and every output matches the R corpus at
   its tolerance class (`closed_form` 1e-9, `iterative` 1e-6).
2. Every calculator output that OpenEpi also shows matches OpenEpi's displayed value at `openepi_display`
   (G7); MEANS on Oswego matches Epi Info 7 at `ei7_display`.
3. Native and wasm results are bit-identical on the whole corpus, including the new families.
4. Every explain view's substituted formula, evaluated by the test suite, reproduces the displayed value at
   the output's tolerance class; explain shows no number the engine did not return.
5. Every exported R script (dataset procedures and calculators, except the random-numbers calculator), run by
   CI in R on the corpus cases, reproduces the engine's values at their tolerance classes.
6. A calculator link opened in a fresh browser profile, offline after the first visit, renders and computes;
   a second tab on a calculator never shows the tab-lock screen.
7. axe: zero violations on every new route and dialog, in all three engines, light and dark; the
   keyboard-only path covers one calculator and one MEANS run.
8. Engine wasm ≤ 409,600 bytes gzip -9 (E3, unchanged); first load < 5 MB gzip (platform §12.8); the
   existing v0.3 perf gates still pass; MEANS on 1M rows gated at an owner-chosen threshold (§10).

**Non-goals for v1.0.** Linear and logistic regression and the data-management commands (v1.1, G2); typed
command entry and `.pgm` parsing (the command line is display-only; the interpreter is v1.3 after
renumbering); charts (dashboards are v1.5); saving calculator results into a project; Stata export unless the
FAU licence allows it (G6); Python export; epidemiologist sign-off (G5); a university pilot (now a running
track, not a version criterion); i18n; regression-based or survey-weighted means.

## 3. Architecture

### 3.1 What changes where

```
crates/
  epiora-core/
    special/      + t, F and gamma distributions, quantiles (§4.1)
    stats/        + means, variance tests, rank tests (§4.2); McNemar, trend, kappa, rates, screening (§5)
    calc/         NEW: calculator registry and one module per calculator family (§5)
    procedures/   + means (§4.3)
    explain/      NEW: explain traces (§6)
    export/       NEW: R script generator and dataset CSV writer (§8)
  epiora-wasm/    + means, calc registry/run, explain, export exports
app/src/
  calc/           NEW: calculator worker, generic form and result renderer, URL state (§7)
  ui/routes/      + /calc, /calc/:id; Analysis gains MEANS
  ui/screens/     + explain panel, command line, export button
fixtures/
  R/              + special v3 grids, means, every calculator family (generate.R)
  openepi/        NEW: OpenEpi displayed values (own workflow, G7)
  ei7/            + MEANS in oswego.pgm
```

### 3.2 Rules carried from v0.2 and v0.3

`libm`-only float maths with the std-float lint; no clock or environment reads in Rust; `Estimate =
Value | Undefined { reason }`, never NaN; clippy denies `unwrap`/`expect`/`panic` outside tests; every
statistic has a registry entry and a fixture; fuzzed inputs; native/wasm parity with no tolerance; files under
~400 lines; the main thread never touches wasm or SQLite; fixtures never change in a commit that touches
`crates/`.

## 4. MEANS

### 4.1 `special` additions

| Function | Method | Reference |
|---|---|---|
| `t_cdf`, `t_sf`, `t_quantile` | via `reg_inc_beta` / `beta_quantile` | R `pt`, `qt` |
| `f_sf` | via `reg_inc_beta` | R `pf(lower.tail = FALSE)` |
| `gamma_quantile`, `chisq_quantile` | Brent on the regularised incomplete gamma | R `qgamma`, `qchisq` |
| `poisson_tail` | via the regularised incomplete gamma | R `ppois` |
| `binomial_quantile` | search on `binomial_tail` | R `qbinom` |

Grids for each go in `fixtures/special/` (Task 2).

### 4.2 Statistics

For a Real, Integer or Date variable, optionally grouped by one categorical variable (Classic Analysis
`MEANS var [crosstab]`):

| Output | Class |
|---|---|
| Per group: observations, total, mean, variance, std dev, minimum, 25th percentile, median, 75th percentile, maximum, mode | closed_form |
| Percentile definition | Epi Info 7's, determined from the EI7 run (Task 4) and recorded with R's `quantile(type = k)` equivalent |
| Two groups: Student t-test (pooled) and Welch/Satterthwaite t-test, each with t, df, p and the 95% CI of the difference | closed_form |
| ≥ 2 groups: one-way ANOVA (between, within, total SS; df; mean squares; F; p) | closed_form |
| Bartlett's test for equality of variances: χ², df, p | closed_form |
| Kruskal–Wallis H with tie correction, df, p (labelled "Mann–Whitney/Wilcoxon" for two groups, as Epi Info does) | closed_form |

Sums use a compensated (Neumaier) summation over the rows in data order, so results are deterministic and
stable at 1M rows. A group with one observation has an undefined variance (`Undefined { too_few }`), not an
error. Dates report means as dates (days since 1970-01-01) and differences in days.

### 4.3 Procedure and receipt

`means(ds, &MeansOptions { variable, group_by: Option<String>, include_missing: bool }, ctx)` →
`ProcOutput<MeansResult>`. Exclusions are counted per variable as for FREQ and TABLES. The receipt format is
unchanged (v1 without a project, v2 with one); the `validation` registry gains every MEANS statistic.

### 4.4 Epi Info 7 check

`fixtures/ei7/oswego.pgm` gains `MEANS AGE` and `MEANS AGE SEX`; `parse.mjs` and `labels.json` learn the MEANS
output; the regenerated `fixtures/ei7/oswego.json` is an owner-reviewed fixture change (Task 4).

## 5. Calculators

### 5.1 Registry

Each calculator is a Rust definition: id (stable, used in the URL), title, family, inputs (name, type,
range, default, unit), validation rules, and output sections (each output with its statistic id, label,
tolerance class and explain trace). `calc::REGISTRY` is exported to the app through `ts-rs` types; the app
renders every calculator from its definition (§7.2). One run function per calculator takes validated inputs
and returns the outputs plus a calculator receipt (§5.4). Adding a calculator is a Rust change plus fixtures
and strings, never a new screen.

### 5.2 Inventory (to be pinned by Task 1)

The union of OpenEpi's menu and Epi Info 7's eight StatCalc calculators. Task 1 confirms the exact list,
inputs, outputs and methods from the live OpenEpi site, OpenEpi's documentation and the Epi Info 7 StatCalc
source (Apache-2.0 with notice, D2), and records it in `docs/v1.0-calculators.md`; the owner reviews it before
any calculator task starts.

| Family | Calculators (expected) | Mostly reuses |
|---|---|---|
| Counts | Proportion (CIs: Wilson, Wilson with CC, Clopper–Pearson, mid-p, Wald); Two by Two Table and 2×n (EI7 Tables), with strata; R by C; Dose-response / chi-square for trend; Matched case-control (McNemar, matched OR with CIs, 1:n matching); Screening test (sensitivity, specificity, PPV, NPV, likelihood ratios, accuracy, with CIs); Standardized mortality ratio; Binomial; Poisson | v0.2 2×2, stratified, R×C, proportions |
| Person time | One rate (with CIs); Compare two rates (rate ratio and difference, exact and mid-p tests) | `poisson_tail`, `gamma_quantile` |
| Continuous (summary data) | Mean CI; Median and percentile CI; t-test from n/mean/sd; ANOVA from n/mean/sd per group | §4 |
| Sample size | Proportion / population survey (with population size and design effect); Unmatched case-control and Cohort/cross-sectional/RCT (Kelsey, Fleiss, Fleiss with CC); Mean difference | `normal_quantile` |
| Power | Unmatched case-control; Cohort/cross-sectional/RCT; Mean difference | `normal_cdf` |
| Other | Random numbers (seeded ChaCha, seed shown and in the URL; platform §7.4). R cannot reproduce a ChaCha stream, so this calculator is checked by a golden output per seed and distribution property tests instead of R fixtures and R export | — |

Epi Info 7 StatCalc is not scriptable (no `.pgm` route), so it is read as a method source only; outputs that
only Epi Info shows (for example the 2×n table and its population-survey formula) are checked against R
implementations of the method found in its source. Where OpenEpi and Epi Info use different methods for the same output, the calculator shows both, as OpenEpi
does, and labels which tool uses which; the method choices are an owner review (Task 13), like v0.2 Task 9.

### 5.3 Inputs

Inputs are validated in Rust (the app also checks ranges for immediate feedback, from the same definition):
counts are non-negative integers below 2^53; proportions in (0, 1); confidence levels from a fixed list
(90, 95, 99%); errors are typed (`calc_input_out_of_range`, `calc_input_missing`, …) and name the input.
Statistically impossible combinations give `Undefined { reason }` outputs, not errors.

### 5.4 Calculator receipts

`receipt_version` 3 replaces the `dataset` block with `"calculator": { "id", "inputs" }` (inputs canonical,
defaults filled in); every other field as receipt v1. Receipts v1 and v2 are unchanged, so no golden changes.

## 6. Explain mode

- **Engine side:** every statistic can return an explain trace: an ordered list of steps, each a formula id
  and the named intermediate values the engine computed (for example the cell counts, `ln(OR)`, its standard
  error, `z`, and the bounds for a Wald CI). Iterative methods (exact and mid-p CIs, conditional MLE) return a
  "method" step with their inputs and result only; explain describes the method in words and does not pretend
  to show a closed form. Traces are not part of the receipt hash.
- **App side:** `app/src/explain/` holds, per formula id, a plain-language paragraph, the formula as MathML
  with slots, and a source citation (a textbook or the reference software's documentation). The panel opens
  from any result row: words first, then "Show the maths" with the run's numbers filled in.
- **Guard:** a Vitest suite evaluates each substituted formula from the trace values and checks it reproduces
  the displayed value at the statistic's tolerance class; every formula id that any registry statistic can
  emit has a template (coverage test).
- **Review:** the texts are marked "pending adviser review" in the validation report (G5).

## 7. App

### 7.1 Calculator worker and routes

| Route | Screen |
|---|---|
| `/calc` | Calculator index grouped by family, with search |
| `/calc/:id?…inputs` | One calculator: form, results, explain, receipt, copy link |

Calculators run in a separate dedicated worker that loads only core-wasm: no store, no import-wasm, no Web
Lock, so any number of calculator tabs work alongside the main app. Opening a calculator link never shows the
lock screen and never creates a database. The service worker precaches the calculator routes with the shell.

### 7.2 Generic calculator screen

Rendered from the registry definition with the existing component set: inputs (labelled, with units and
range hints), a Calculate button, and results as semantic tables (caption, scope) in the result-card style of
v0.3, each row with an explain button. Inputs are written to the URL query on calculate; opening a link with
inputs computes immediately. Layout works at 320px (phone use in the field).

### 7.3 Analysis workspace

- MEANS joins FREQ and TABLES in the procedure menu: a dialog with the variable, optional group-by variable
  and missing handling; the card shows the descriptive table per group and the test tables.
- **Command line (G4):** every card shows its Epi Info command (`FREQ SEX`, `TABLES VANILLA ILL
  STRATAVAR=SEX`, `MEANS AGE SEX`), generated in Rust from the canonical options, stored with the run, with
  "Copy". Existing runs get theirs generated on load (not stored retroactively).
- Each card gains "Explain" (per row) and "Export to R" (§8).

## 8. Reproduce in R (and Stata if licensed)

### 8.1 Generator

Rust (`epiora-core::export`) produces, from a run's canonical options: `data.csv` (the exact dataset version,
written deterministically with explicit missing codes) and `analysis.R`, which reads it with explicit column
types, runs the same reference functions that generate the corpus fixtures for those statistics, prints the
results labelled as in Epiora, and checks the row count. Calculator exports produce `analysis.R` only. Where
no published R package implements a method (for example Kelsey/Fleiss sample sizes or OpenEpi-style
intervals), the script carries the same R function `fixtures/R/` uses to generate that fixture, copied from
one shared source file so the corpus and the exports cannot drift; these R snippets are licensed MIT so users
can reuse their scripts freely (a header line says so). The
script header names the receipt hash, Epiora's engine version and the R packages required.

### 8.2 App

"Export to R" downloads `epiora-<procedure>-<receipt hash prefix>.zip` (`data.csv`, `analysis.R`,
`receipt.json`), zipped in the worker with `fflate`.

### 8.3 Verification

- **R (CI):** a job generates the export for every corpus case (dataset procedures and calculators), runs each `analysis.R` under the renv-pinned
  R, parses its labelled output and compares it with the engine at each statistic's tolerance class. Any
  mismatch fails CI.
- **Stata (conditional, G6):** if no FAU answer is recorded when Task 17 merges, Task 20 records Stata as
  deferred and v1.0 closes without it. Otherwise, only after the owner records in `docs/decisions.md` that FAU permits it. Then
  `export` gains a `.do` generator; `scripts/stata/verify.sh` (human step, owner's laptop) runs every corpus
  `.do` and writes `fixtures/stata/results.json` plus the SHA-256 of each `.do` it ran; CI fails if any
  generated `.do` differs from the hashed one, so a changed exporter is red until re-verified. Until then the
  app offers R only.

## 9. OpenEpi as a reference (G7)

`fixtures/openepi/` is produced by its own `workflow_dispatch` workflow: Playwright opens each OpenEpi
calculator page, enters the inputs of each case in `fixtures/openepi/cases.json`, and records every displayed
number and its decimal count. Committed as an owner-reviewed fixture (Task 3), re-run monthly on a schedule,
failing on any diff. Task 1 records OpenEpi's terms of use; if automated access is not permitted, the owner
captures the values by hand as a human step with the same file format. Comparison rule: pass iff
`|engine − openepi| ≤ 0.5 × 10^−d`.

## 10. CI, budgets and testing

  extended corpus; new fuzz targets `calc_any` (any calculator id with arbitrary inputs) and `means_any`.
- `fixtures.yml`: unchanged rule (regenerate, validate, fail on diff), covering the new families.
- New `r-export.yml` job (§8.3); `openepi.yml` (§9); the EI7 workflow runs the extended `.pgm`.
- `app.yml`: calculator routes, MEANS dialog and explain panel in Playwright on three engines with axe; the

- **Budgets:** engine wasm ≤ 409,600 bytes (unchanged); first load < 5 MB; v0.3 gates unchanged. New:

- **Validation report** `docs/validation/v1.0.md`, generated by CI like v0.2/v0.3: every statistic with its

## 11. Error handling

New `EngineError` codes: `calc_unknown`, `calc_input_out_of_range`, `calc_input_missing`,
`not_numeric_variable`, `too_many_groups` (MEANS group-by above 100 levels). Undefined statistics stay inside
successful results. The calculator worker maps errors to the same typed RPC errors as the data worker; a
malformed calculator URL shows the form with the bad input marked, never a blank page.

   synthetic data. → Tasks 6, 11.
