## 1. Intent

**Outcome.** The first usable Epiora: an installable, fully offline web app and an unsigned desktop app that
let a user create a project, import a CSV/TSV or spreadsheet, keep its versions, and run v0.2's FREQ and TABLES
from a dialog-driven Analysis workspace whose results and receipts are saved. It is an internal foundation
with a deployed preview, not a public release.

**Who it is for.** The owner and early testers (preview URL and desktop artifacts); every later phase, which
builds on the store, change log, worker and design system defined here.

**Success criteria.**
1. Import → version → analysis → saved result + receipt works end to end, offline, in Chromium, Firefox and
   WebKit (Playwright), and in the Tauri desktop build (Linux smoke test).
2. The same store conformance suite passes on both backends (OPFS sqlite-wasm and native SQLite3MultipleCiphers).
3. Re-importing a changed file produces a correct record-level diff and a new version; re-importing an
   unchanged file produces no new version.
4. Every import fixture parses to its expected JSON, natively and in wasm, bit-identically.
5. axe reports zero violations on every route and dialog in all three engines, light and dark; every token
   colour pair meets WCAG 2.1 AA (high-contrast themes 7:1).
6. First load is under 5 MB gzipped (platform §12.8); import-wasm, 1M×10 import and open + TABLES on 1M rows
   are gated at owner-chosen thresholds set from a measurement task (§10.3).
7. The desktop database is encrypted at rest with a key from the OS keychain; the file carries no plaintext
   SQLite header.

**Non-goals for v0.3.** Data editing and derived variables; charts; export to Word/PDF; command or `.pgm`
entry; DuckDB-wasm (D3: lazy analytics engine, later); SPSS/Stata/SAS/Parquet import (v1.5); sync and
multi-user (v2.0); field-level browser encryption (D6, §7.6); desktop signing, notarisation and auto-update
(v1.2); passphrase or key recovery (v2.1); i18n framework; thousands separators.

## 3. Architecture

### 3.1 Repository layout

```
crates/
  epiora-core/         (v0.2) + snapshot codec: Dataset ⇄ columnar bytes (§5.1)
  epiora-wasm/         (v0.2) + datasetFromSnapshot / datasetToSnapshot
  epiora-import/       NEW: CSV/TSV (csv + encoding_rs), xlsx/xls/ods (calamine), detection,
                       type inference, coercion, record keys, re-import diff
  epiora-import-wasm/  NEW: thin binding; its own lazily loaded .wasm; size gate
app/                   NEW: Vite + React + TypeScript
  src/ui/              routes, screens, Epiora components on React Aria
  src/design/          tokens.json → CSS variables; contrast test
  src/worker/          the data worker: RPC surface, import and analysis orchestration
  src/store/           Store interface, OPFS backend, Tauri backend client, conformance suite
  src-tauri/           Tauri 2 shell: native SQLite3MultipleCiphers store commands, keychain
store/migrations/      shared SQL schema, one source for both backends
```

### 3.2 Flows

- **Import:** file bytes → import-wasm (detect, preview, infer, coerce, diff) → typed columns → store writes
  records + change log + version + snapshot in one transaction.
- **Analysis:** store snapshot blob → core-wasm `datasetFromSnapshot` → hash check → `freq`/`tables` →
  result + receipt → `runs`.

### 3.3 Rules carried from v0.2

Both Rust crates: no clock or environment reads; `libm`-only floats where floats appear; clippy denies
`unwrap`/`expect`/`panic` outside tests; fuzzed; native/wasm parity; AGPL-compatible licences checked by
`cargo-deny`. Timestamps come from the worker, never from Rust.

## 4. Store

### 4.1 Schema (`store/migrations/*.sql`, shared by both backends)

| Table | Holds |
|---|---|
| `projects` | id (UUID), name, created_at, updated_at |
| `datasets` | id, project_id, name, key column (or row position), saved import settings (JSON), current_version |
| `dataset_versions` | dataset_id, version, source file name, source SHA-256, row count, engine content hash, snapshot blob, snapshot_available |
| `records` | current state: dataset_id, record_id, values (canonical JSON), version last changed |
| `changes` | append-only: seq, change_id (UUID), dataset_id, record_id, kind `insert\|update\|delete`, field (null for insert/delete), value, base_version, author, device_id, lamport, import_id |
| `imports` | id, dataset_id, resulting version, settings used, per-column coercion counts, detected encoding/delimiter/sheet, created_at |
| `runs` | the output log: id, project_id, procedure, options, dataset_id, dataset version, result JSON, receipt JSON, receipt hash, created_at, deleted_at |
| `meta` | schema version, device_id (generated once per install), lamport clock |

Migrations are numbered, forward-only, and applied in one transaction at connect; the schema version is in
`meta`.

### 4.2 Change entries

- **First import:** one `insert` per record carrying all fields (1M rows → 1M entries, not 10M).
- **Re-import:** diff against current `records` by key: new record → `insert`; changed field → `update` on
  that field with `base_version`; missing record → `delete` (tombstone). An unchanged file creates no
  version.
- **Author / device:** author is `local`, device_id is per install; the shape matches platform §7.3 so v2.0
  sync can consume it.

### 4.3 Source of truth and snapshots

`records` + `changes` are the source of truth. The snapshot is a derived cache written when a version is
created. On load, the engine's content hash is compared with the stored hash; on mismatch or decode error,
the latest version's snapshot is rebuilt from `records` and older versions are marked
`snapshot_available = 0`. Receipts use `dataset.version` and the content hash.

### 4.4 Record keys

The user picks a key column or row position (`row:N`). Duplicate or missing keys are shown in the preview
and block that key choice (no silent merges). Row-position keys make re-import a positional diff; the
preview warns.

### 4.5 Rules and conformance

Every version-creating write is one transaction. The conformance suite runs the same tests on OPFS and on
native: schema and migrations, transactional import and rollback on cancel, the diff, tombstones, snapshot
rebuild, and run persistence.

## 5. Snapshot, engine loading and the data worker

### 5.1 Snapshot format (`epiora-core`)

Header: magic `EPSN`, format version, row count, column count. Per column: name, type
(Integer/Real/Text/Boolean/Date), missing bitmap, little-endian values; Text as offsets + UTF-8 bytes. The
layout reuses v0.2's canonical-bytes ordering, so encode → decode → `datasetHash` reproduces the content
hash; property tests and a fuzz target check the round trip. `epiora-wasm` gains `datasetFromSnapshot(bytes)`
→ handle and `datasetToSnapshot(handle)`; the import side uses the same codec (one encoder). Decode failure
and hash mismatch are typed errors.

### 5.2 Data worker

One dedicated Web Worker (the same code in Tauri's webview) owns core-wasm (loaded at worker start),
import-wasm (loaded lazily on the first import screen) and the store client (sqlite-wasm OPFS in the browser;
Rust commands in Tauri). Tauri's IPC is not available inside a Web Worker, so in Tauri the worker's store
client relays each store call through a small main-thread bridge that calls `invoke` and transfers the
result back; the bridge relays bytes only and holds no logic. It keeps an LRU of 2 loaded dataset handles. The main thread never
touches wasm or SQLite.

### 5.3 RPC surface (typed, Comlink-style; request/response plus progress events)

| Area | Calls |
|---|---|
| Projects | `listProjects`, `createProject`, `renameProject`, `deleteProject` |
| Datasets | `listDatasets(project)`, `getDataset`, `listVersions`, `getVersionPage(version, offset, limit)` |
| Import | `inspectFile(bytes)` → detection + preview + inferred types; `previewWithSettings(settings)`; `diffAgainst(dataset, settings)`; `commitImport(…)` with progress + cancel |
| Analysis | `runFreq(version, options)`, `runTables(version, options)` → result + receipt, saved to `runs` |
| Output log | `listRuns(project)`, `rerun(run, newVersion)`, `deleteRun` |
| System | `engineVersion`, `storageEstimate`, `tabLockStatus` |

- **Errors:** typed codes (`ImportError`, `StoreError`, `EngineError`, `HashMismatch`, `Cancelled`) with
  user-facing messages; Rust errors map to these in one place.
- **Types:** generated from Rust (`ts-rs` or `tsify`) for everything crossing a wasm boundary; the rest is
  hand-written TS checked by a contract test.
- **Cancellation:** long imports run in chunks and check a cancel flag between chunks; a cancelled import
  rolls back its transaction.

## 6. Import (`epiora-import`)

### 6.1 Detection (deterministic; first 64 KiB plus file magic)

1. Container: zip magic → xlsx/ods; OLE magic → xls; else text.
2. Encoding: BOM → UTF-8/UTF-16; else valid UTF-8 → UTF-8; else Windows-1252. Overridable.
3. Delimiter: among `,` `;` tab `|`, the most consistent per-line field count over the sample; ties broken in
   that order. The `.tsv` extension is a hint only.
4. Header row: on by default (toggle). Empty or duplicate names become unique (`x`, `x_2`) and are reported.
5. Spreadsheets: list sheets, default to the first, read the used range; merged cells and formulas use cached
   values.

### 6.2 Type inference (per column, over all rows)

Candidates in order Boolean → Integer → Real → Date → Text; the first that every non-missing value fits wins.

- **Missing:** empty plus the user list (default empty, `.`, `NA`).
- **Integer:** optional sign + digits, fits i64.
- **Real:** decimal separator detected (comma when `;` is the delimiter and commas parse as decimals),
  overridable; no thousands separators in v0.3.
- **Boolean:** `true/false`, `TRUE/FALSE`, `yes/no` only; `0/1` stays Integer.
- **Date:** ISO `YYYY-MM-DD` by default; `DD/MM/YYYY` or `MM/DD/YYYY` only when the user picks it (no
  guessing); Excel date-formatted cells via the serial number (1900 and 1904 systems).
- **Overrides:** any column to any type; non-conforming values become missing with per-column counts in the
  preview and on the `imports` row.

### 6.3 Determinism and limits

No clock, environment or locale reads; the file SHA-256 is recorded. Errors above 2^31 rows or 16,384
columns. Large files stream in chunks. Ragged rows are an error with line number and sample; no silent
padding.

### 6.4 Re-import

Saved settings apply automatically. The diff preview shows added/changed/removed counts, the first N changes
per field, and schema changes (column added or removed, type changed), which must be accepted explicitly.

### 6.5 Tests

Fixture corpus `fixtures/import/` (each file with expected JSON): every encoding, each delimiter, decimal
comma, xlsx/xls/ods, Excel dates in both systems, ragged rows, BOM, duplicate headers. `cargo-fuzz` targets for
the CSV and spreadsheet entry points. Native/wasm parity on the corpus.

## 7. Platform shells

### 7.1 PWA

- Manifest (name, icons, `display: standalone`); installable in Chromium; Safari/Firefox get add-to-home and
  offline.
- Service worker via `vite-plugin-pwa` (Workbox) precaches the shell, core-wasm, import-wasm and sqlite-wasm.
  Updates prompt "New version available — reload"; never a silent swap mid-session.
- Offline Playwright test: load, go offline, reload, import, run TABLES.
- `navigator.storage.persist()` requested on first import; Settings shows usage, quota and whether
  persistence was granted.
- One tab: OPFS sahpool allows one connection; a Web Lock (`navigator.locks`) detects a second tab, which
  shows "Epiora is open in another tab" with "Use here" (lock handover).

### 7.2 Netlify

`netlify.toml`: build command, publish `app/dist`, SPA fallback; `_headers` with long cache for hashed assets,
no-cache for `index.html` and `sw.js`, and a strict CSP (`wasm-unsafe-eval`, no third-party origins).
Deploys run from GitHub Actions (`netlify deploy`) after the gates: preview per PR, production on `main`.
**(human step)** The owner creates the site and adds `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID`.

### 7.3 Tauri 2 desktop (`app/src-tauri`)

- Loads the same `app/dist`, worker and wasm modules.
- Store: a Rust crate `epiora-store-native` (in the `app/src-tauri` Cargo workspace, which carries the
  `libsqlite3-sys` patch so the engine workspace does not) implements a generic SQL executor; the shared
  TypeScript repositories run on top of it exactly as on OPFS. A test-only `store-stdio` binary exposes the
  same executor over stdin/stdout so the TypeScript conformance suite runs against native SQLite3MC in CI.
- Store commands (`store_exec`, `store_query`, `store_tx_*`, `store_snapshot_get/put`) on native
  SQLite3MultipleCiphers via `rusqlite` with the vendored, patched `libsqlite3-sys` (Tauri spike). The key is
  applied once at connect (`PRAGMA key` + cipher settings) and verified with a read; commands never carry the
  key. Snapshot blobs cross IPC as raw bytes, not JSON.
- Key: 32 random bytes from the OS RNG on first launch, stored in the OS keychain via `keyring`. Keychain
  unavailable → clear error, no plaintext fallback. Losing the key loses the data (stated in the UI and
  docs); recovery is v2.1.
- Database in the app data dir. Capabilities: dialog open (file pick) and the store commands only; no shell,
  no HTTP.
- `src-tauri/gen` is generated in CI, not committed.

### 7.4 Browser encryption

v0.3 does not encrypt browser databases. D6 field-level `fieldCrypto` is not used yet because v0.3 has no
identifiable-field marking; it becomes required with the first version that marks identifiable fields
(open decision, §14).

## 8. Screens and the Analysis workspace

### 8.1 Routes (TanStack Router)

| Route | Screen |
|---|---|
| `/` | Projects: list, create, rename, delete |
| `/p/:project` | Project home: datasets with version history; output log |
| `/p/:project/import` | Import wizard: choose file → detect/preview → settings → (re-import) diff → confirm → progress |
| `/p/:project/d/:dataset` | Data view: virtualised read-only grid over `getVersionPage`; version selector; per-column type and missing counts |
| `/p/:project/analysis` | Analysis workspace |
| `/settings` | Theme (light, dark, system, high contrast), storage use, engine version |

### 8.2 Analysis workspace

- Left: dataset and version picker; procedure menu (FREQ, TABLES, as v0.2).
- Each procedure opens a React Aria dialog: FREQ — variables, missing handling; TABLES — row and column
  variables plus v0.2 options (percentages, χ²/Fisher, OR/RR with CI).
- Run appends a result card to the output log (right, newest first): title (procedure, variables,
  `dataset vN`), timestamp; result tables as semantic `<table>` (caption, scope, headers); a collapsible
  receipt (engine version, dataset content hash, options, receipt hash, "Copy receipt JSON"); a badge when a
  newer version exists with "Rerun on vN+1", which adds a new card and leaves the old one.
- Receipts name the project (F12): `receipt_version` 2 is v1 plus `"project": {"id", "name"}`. A run with no
  project (the corpus, parity and v0.2 goldens) still emits exact receipt v1, so v0.2 goldens do not change.
- The output log persists per project in `runs` and reloads exactly; card deletion is recorded
  (`deleted_at`).
- Errors show inline on the card or dialog with the typed message and a retry; empty states (no projects,
  datasets, runs) offer the next action.

## 9. Design system and accessibility

### 9.1 Tokens

`app/src/design/tokens.json`: colour, spacing (4px scale), radius, type scale, system font stacks (no web
fonts), motion, focus ring. A build step generates CSS custom properties for `light`, `dark`, `hc-light`,
`hc-dark`; `prefers-color-scheme` and `prefers-contrast: more` choose the default; Settings overrides.
`prefers-reduced-motion` disables transitions.

### 9.2 Components and lint

React Aria Components wrapped as Button, TextField, Select, ComboBox, Checkbox, RadioGroup, Dialog, Menu,
Tabs, Table, ProgressBar, Toast, Disclosure, FileTrigger. Screens use only these (ESLint bans bare
`<button>`, `<input>`, `<select>` outside the component set). CSS modules reference tokens only; Stylelint
bans raw hex/rgb/hsl colours and raw px for spacing, radius and font size outside `tokens`.

### 9.3 Accessibility (WCAG 2.1 AA, platform §11.1)

- Contrast test (Vitest) on every declared text/background and UI/background pair: 4.5:1 text, 3:1 large text
  and UI; 7:1 in high-contrast themes.
- Playwright + axe on every route and dialog, Chromium/Firefox/WebKit, light and dark; zero violations; any
  allow-list entry requires a `docs/decisions.md` entry.
- Keyboard-only path test: create project → import CSV → run TABLES → expand receipt, with visible focus.
- Live-region announcements for progress and results; dialogs titled, focus-trapped, focus-returning;
  layouts work at 320px width and 200% zoom (Playwright viewport test).
- UI strings in one English module (no i18n framework yet).

## 11. Error handling

- Rust: `Result<_, ImportError>` / `EngineError` with stable codes (`encoding_invalid`, `ragged_row`,
  `too_many_columns`, `duplicate_key`, `missing_key`, `sheet_not_found`, `snapshot_decode`, …); no panics on
  input paths.
- Store: `StoreError` codes (`migration_failed`, `tx_aborted`, `locked_elsewhere`, `quota_exceeded`,
  `keychain_unavailable`, `key_invalid`).
- Worker: maps all of the above into the typed RPC errors (§5.3), each with a user-facing message; the UI
  never shows a raw stack trace.

## 15. Review focus (for the plan)

1. **Silent data change on import** — expect non-conforming values to become counted missing, ragged rows to
   error, duplicate keys to block, and schema changes to need explicit acceptance. → Tasks 2–5, 11.
2. **Snapshot drift** — expect a hash check on every load and a rebuild from `records`, never a run on a
   snapshot whose hash differs from the version's. → Tasks 1, 9.
3. **Backend divergence** — expect one conformance file run on both backends; any backend-only test is a
   finding. → Tasks 8, 14.
4. **Key handling on desktop** — expect the key never to cross IPC or appear in logs, no plaintext fallback,
   and the plaintext-header check in CI. → Tasks 14, 15.
5. **Accessibility regressions hidden by allow-lists** — expect zero axe violations and no allow-list entry
   without a decisions record. → Tasks 7, 10–13.
6. **Thresholds set from prose** — expect perf and size numbers only from linked CI runs, and gates only after
   the owner picks thresholds. → Tasks 16, 17.
7. **Ambiguous dates** — expect no date-format guessing; non-ISO dates parse only with an explicit user
   choice. → Tasks 2–4.
