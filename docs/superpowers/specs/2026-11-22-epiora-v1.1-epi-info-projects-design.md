## 1. Intent

**Why.** CDC ended Epi Info in September 2025 and offers no replacement and no migration path. The users it
stranded (LMIC ministries, field epidemiology training programmes, small health departments) still hold Epi
Info projects and `.pgm` analysis scripts. Nobody else opens those projects today (2026-11-22 delta): Epi Info
AI converts `.mdb` tables only, and no tool reads the project structure. v1.1 is the version where an Epi
Info user can bring their project into Epiora, keep cleaning and analysing it with the commands they know,
re-run their old scripts, and see, command by command, how Epiora's results compare with Epi Info 7.

**Owner direction.** Goals for Epiora: wide use, side income, grant funding. Features and UI mature before the
public launch, which waits for v1.6 together with the adviser, the first pilot and the Digital Public Good
application. So v1.1 ships as a pre-release, like v1.0, and its job is completeness and correctness, not
launch polish. Full Epi Info 7 parity is required by v1.6; v1.1 makes that checkable (G4).

**Outcome.** A pre-release of the web and desktop app in which:
- Epi Info 7 projects stored in Access (`.mdb`) or SQLite (`.db`) open in the browser and on desktop, and
  Epi Info 7 projects stored in SQL Server open on desktop; Epi Info 3.5.x projects (`.mdb`) open in both;
- each form (view) becomes a dataset with its field types, value labels, yes/no fields and code tables;
  child forms and grids become linked datasets; saved programs and check code come along;
- SELECT, SORT, RECODE, DEFINE, ASSIGN, MERGE and RELATE work, from dialogs and typed commands;
- a program editor opens and runs `.pgm` scripts; every command Epiora does not support yet is listed with
  the version that brings it, never skipped silently;
- a migration report per project says what was imported, what was not and why, and how each analysis
  command's results compare with Epi Info 7;
- every result keeps a receipt that reproduces it exactly, including the cleaning steps behind it.

**Who it is for.** Stranded Epi Info 7 and 3.5.x users; v1.0 users with CSV/Excel data who need cleaning
commands; v1.2 (MCP server and CLI), which calls the same engine code.

**Success criteria.**
1. Every Epi Info 7 Classic Analysis command, and every user-facing Epi Info 7 module feature, is in an
   owner-reviewed register with a target version no later than v1.6 (Task 1).
2. Every bundled Epi Info 7 sample project (21 `.prj`; 18 Access, 1 SQLite, others as Task 2 lists) and the
   Epi Info 3.5.4 tutorial projects (subject to D12, §8.2) import with no error, and each imported dataset
   matches its golden fixture (schema, labels, row count, content hash).
3. Each Access sample, copied table-for-table into SQLite and into SQL Server (CI container) by a copy script
   that does no mapping (§8.2), imports to identical dataset hashes from all three.
3a. Re-importing a newer copy of an Access or SQLite project creates new dataset versions in the same
   project, with the v0.3 re-import diff keyed on `GlobalRecordId`; an unchanged file creates nothing.
4. Every supported command in the Epi Info 7 reference programs (Task 3) matches Epi Info 7 at `ei7_display`
   and R at its tolerance class where R has the statistic; native and wasm results are bit-identical.
5. A `.pgm` containing unsupported commands runs the supported ones and lists every unsupported one, with
   its line and target version; it never fails silently and never runs a partial command.
6. Every result computed on a cleaned working view has a receipt naming the source dataset hash, the recipe
   hash and the working-view hash; re-running the recipe on the source reproduces the working-view hash.
7. A truncated, corrupt, password-protected or unsupported file gives a typed error that names the format;
   fuzzing the metadata mapper and the `.pgm` parser finds no panic.
8. Exported R scripts for results on a working view reproduce the engine's values in CI (v1.0 rule).
9. axe: zero violations on every new route and dialog, three engines, light and dark; the keyboard-only path
   covers one legacy import, one RECODE and one program run.
10. Engine wasm stays within its budget (§9); the mdb reader loads only on the legacy-import screen; legacy
    import of a large synthetic project is gated at an owner-chosen threshold (Task 19).

**Non-goals for v1.1.** Writing `.mdb` files (platform A5, never); running check code or data entry (v1.3);
editing form definitions (v1.3); GRAPH, MAP and dashboards (v1.4); regression and the DAG helper (v1.2);
decrypting fields Epi Info encrypted with a project password (listed in the migration report; revisit on
demand); SQL Server from the browser; Epi Info 7 web/cloud (`Epi Info Web Survey`) data; Epi Info for DOS
(`.rec`) files; the public launch and pilot (v1.6); translating cleaning recipes into R (§8.3).

### 3.2 Rules carried from v0.2–v1.0

`libm`-only float maths with the std-float lint; no clock or environment reads in Rust; `Estimate = Value |
Undefined { reason }`; clippy denies `unwrap`/`expect`/`panic` outside tests; every statistic has a registry
entry and a fixture; fuzzed inputs; native/wasm parity with no tolerance; files under ~400 lines; the main
thread never touches wasm or SQLite; fixtures never change in a commit that touches `crates/`; never-loosened
tolerances.

## 4. Opening legacy projects

### 4.1 Readers

| Source | Reader | Where |
|---|---|---|
| Epi Info 7 Access (`.mdb`, JET4) | `epiora-mdb` | browser and desktop |
| Epi Info 3.5.x Access (`.mdb`, JET3 or JET4) | `epiora-mdb` | browser and desktop |
| Epi Info 7 SQLite (`.db`) | SQLite already shipped (sqlite-wasm; native in Tauri) | browser and desktop |
| Epi Info 7 SQL Server | `tiberius` in the Tauri backend; user enters server, database, authentication | desktop only |

`epiora-mdb` productionises the v0.1 spike: a reproducible Emscripten build of mdbtools' `libmdb` (library
only, not the GPL utilities) with pinned toolchain and checksums, a native build for desktop and tests, and a
small typed API (`format`, `tables`, `schema(table)`, `rows(table, chunk)`) returning typed values rather than
CSV text. Only the wasm module is distributed, in the browser and in the desktop webview alike; the native
build serves tests, fuzzing and the golden-dump tooling and is never shipped (LGPL: the module stays
replaceable without relinking; the source offer ships with it). Errors: `mdb_truncated`, `mdb_corrupt`, `mdb_password_protected`, `mdb_unsupported_version`, each
naming the detected format.

Every reader produces the same intermediate form (tables with typed columns), so the mapper (§4.2) is written
once.

### 4.2 Metadata mapper (`epiora-legacy`)

- **Epi Info 7.** Reads the `meta*` tables (views, pages, fields, code tables, programs, grid columns,
  relations) and the per-page data tables joined on `GlobalRecordId`. The Epi Info 7 source
  (`Epi.Core`, Apache-2.0, D2) is the method source for the layout; no code is copied without the notice.
- **Epi Info 3.5.x.** Reads the Epi Info 3 layout following CDC's own upgrade code
  (`Epi.ImportExport/Epi2000/`, `ProjectUpgradeManager`), mapping it to the same Epiora structures.
- **Output:** one Epiora project per legacy project (identified by the legacy project id and file name, so a
  re-import finds it); one dataset per view; child views (Relate fields) and
  grids become linked datasets keyed by `FKEY` → parent `GlobalRecordId`; saved programs become program
  documents (§7.2); check code is stored per view.
- **Field types:** Text, Uppercase, Multiline, GUID → Text; Number → Integer or Real (from the field's
  pattern and the data); Date → Date; Time → Time; DateTime → DateTime; YesNo and Checkbox → Boolean;
  Option, Legal Values, Comment Legal, Codes → the stored value with a value-label set; Phone Number →
  Text; Image and other binary fields → not imported, counted in the report; Mirror → its source value;
  Label, Group, Command Button → form metadata only. Anything else → Text with a report entry. Task 1
  confirms the full list from the source.
- **Never silent:** every legacy field, table, program, check-code block and record that is not imported, or
  imported in a changed form, gets a migration-report entry (§6.2) with the reason.

### 4.3 Dataset model additions

- Value types `Time` (seconds since midnight) and `DateTime` (seconds since 1970-01-01, no time zone, as
  Epi Info stores it), with new hash tags; snapshot format version bump with a migration of stored
  snapshots.
- Per-column metadata outside the value data: prompt (question text), legacy field type, value-label set,
  code-table reference, legacy name. Labels are part of the dataset hash (they change what results display);
  prompts and legacy names are not (the hash rule and its reason go in `docs/decisions.md`).
- Links between datasets (parent, child key column, parent key column), stored in the project.
- Deleted records (`RECSTATUS = 0`) are imported with a hidden status column and excluded by default, as Epi
  Info does; a setting includes them.

### 4.4 Check code

Imported as text per view, shown read-only beside the dataset, and listed in the migration report. It is not
parsed for execution in v1.1; v1.3 translates it with the expression language from §5.2. v1.1 parses it only
far enough to count blocks, so the report can say what v1.3 will need to translate.

### 4.5 Refresh (G8)

"Re-import" on a legacy project takes a newer `.mdb` or `.db` of the same project, maps it, and diffs each
view against its latest dataset version with the v0.3 re-import diff, keyed on `GlobalRecordId` (always
present in Epi Info 7 data tables; Epi Info 3.5.x uses its `UniqueKey`). The preview shows added, changed and
deleted records and any schema change per view; confirming creates new versions in one transaction. Form
changes (fields added or retyped) are shown and applied as schema changes with report entries; a view that
no longer exists is kept and marked. SQL Server projects are not refreshable; their credentials are held in
memory for the import only, never written to the store, settings or logs.

## 5. Data management

### 5.1 Working view and recipe (G3)

Each Analysis session has a working view: a source dataset version plus an ordered recipe of cleaning
commands. Every command appends to the recipe and the engine materialises the view incrementally. The saved
dataset never changes. WRITE (or "Save as new version") materialises the view as a new dataset version through
the v0.3 version path, with the recipe recorded on the version.

Working views persist: each Analysis session (source version, recipe, as-of date) is saved in the store, so
a reload or restart restores it; the v0.3 store migration adds the table. Epi Info's PERMANENT variables
(DEFINE … PERMANENT) are stored per project and enter every session's recipe as explicit DEFINE steps, so
receipts stay self-contained.

A recipe is canonical text: Epi Info commands as Epiora prints them (one canonical spelling per command and
option, as the v1.0 command line does), plus the as-of date (§5.3). Its hash is the SHA-256 of that text.

### 5.2 Expression language (`expr`)

The Epi Info 7 Analysis expression grammar (`Epi.Core.Interpreter/grammar/EpiInfo.Analysis.Grammar.grm`,
Apache-2.0) is the reference. Epiora parses it with a hand-written Rust parser (no GOLD runtime) into a typed
AST. It covers arithmetic, comparison, logical operators, `(.)` missing, string concatenation, and the
functions in the Epi Info 7 Analysis grammar (date parts and differences such as YEARS, MONTHS, DAYS; ROUND,
TRUNC, ABS, EXP, LN, LOG; SUBSTRING, UPPERCASE, FORMAT, and the rest), all of them in v1.1 except any whose
meaning depends on a later feature (for example form or entry state); the Task 1 register lists those with
their version. Missing-value
propagation follows Epi Info 7, checked against the reference programs; where Epi Info 7 behaves
unexpectedly, the choice is an owner review (Task 14). v1.3's check code reuses this module.

### 5.3 Commands

| Command | v1.1 behaviour |
|---|---|
| SELECT / CANCEL SELECT | Filter rows by an expression; repeated SELECTs combine with AND, as in Epi Info |
| SORT / CANCEL SORT | Stable multi-key sort, ascending or descending; missing sorts as Epi Info 7 does |
| DEFINE / UNDEFINE | New variable (typed; standard or global scope as in Epi Info) |
| ASSIGN | Set a variable from an expression, optionally under IF |
| RECODE | Values or ranges (LOVALUE, HIVALUE, ELSE) to new values; boundary handling as Epi Info 7 |
| IF … THEN … ELSE … END | Conditional ASSIGN, DEFINE and other cleaning commands |
| MERGE | Join another dataset by key variables (update and append modes as in Epi Info) |
| RELATE | Bring a linked child or parent dataset into the view by its key |
| READ / WRITE | Open a dataset (or a legacy table by name); save the working view as a new version |
| LIST, DISPLAY | Show the working view (or selected variables) in the grid; show variables, datasets or the recipe |
| DELETE | Remove records matching an expression from the working view (WRITE makes it permanent in a new version); delete variables |
| KEYVARS | Key variables for MERGE and RELATE |
| SET | The options that change results (missing-value inclusion, yes/no and percent display, statistics level as Epi Info defines them); options with no effect on numbers are recorded as notes |
| CANCEL READ and the other CANCEL forms | As in Epi Info |
| FREQ, TABLES, MEANS | Unchanged procedures, now run on the working view |

This table is v1.1's minimum. Task 1's register may add commands that common programs need and that need no
later feature; its owner review is the scope checkpoint, and the plan is revised after it if the scope grows.

Clock functions (`SYSTEMDATE`, `SYSTEMTIME`) read the recipe's as-of value, set when the session starts and
recorded in the recipe, so a re-run gives the same answer (platform §7.4: no clock in the engine).

### 5.4 Receipts v4

Results on a working view carry: source dataset id, version and hash; recipe text and hash; working-view hash;
then the existing procedure, options, engine version and validation reference. Re-running the recipe on the
source must reproduce the working-view hash (success criterion 6). Results on an unmodified dataset keep the
current dataset receipt shape (the recipe fields are absent), so existing golden receipts do not change.

## 6. Programs (`.pgm`) and the migration report

### 6.1 Interpreter

- **Parser:** the full Epi Info 7 Analysis grammar, so every valid Epi Info program parses, including
  commands Epiora does not run yet. Parsing never depends on support.
- **Command register (Task 1):** every command with its status (`supported`, `planned: vX.Y`,
  `not planned` with a reason) and, for supported commands, the options supported. It drives the interpreter,
  the editor's warnings and the migration report, and it is published in the app next to the validation page.
- **Running:** commands run in order. An unsupported command stops nothing: it is reported (line, command,
  target version) and skipped, and every later result whose working view could have been changed by it is
  marked "may differ from Epi Info" (for example, an unsupported data command before a FREQ). Output
  commands with no effect on numbers (TYPEOUT, HEADER, ROUTEOUT, CLOSEOUT and similar) are recorded and shown
  as notes.
- **Sources:** programs saved inside a legacy project, `.pgm`/`.pgm7` files, and text typed or pasted in the
  editor.

### 6.2 Migration report

One per imported project, viewable in the app and downloadable as HTML (Typst reports are v1.6):
1. **Import:** each view, its record count, each field's legacy and Epiora type, and every item not imported
   or changed (§4.2), with reasons.
2. **Programs:** each saved program with its supported and unsupported commands.
3. **Validation:** for each analysis command the project's programs use, the validation-page entry (method,
   references, worst observed error against Epi Info 7 and R from CI).
4. **Your own output (optional):** if the user adds the HTML output files Epi Info 7 saved for the project,
   Epiora re-runs the programs and compares each number it can match, reusing the v0.2 EI7 output parser
   (`fixtures/ei7/parse.mjs`, ported to the app). Matches at `ei7_display` show as equal; differences are
   listed with both values. This turns "trust us" into the user's own numbers side by side.

## 7. App

### 7.1 Legacy import flow

- From the projects screen: "Open an Epi Info project". The user picks the `.mdb`/`.db` (and optionally the
  `.prj` and output files). Desktop also offers "Connect to SQL Server".
- The mdb reader and mapper load lazily; progress, cancel and rollback follow the v0.3 import rules.
- A preview shows the views, fields, record counts and every report entry before anything is written; then
  one transaction creates the project, datasets, links, programs and check code.
- A legacy project's page has "Re-import a newer copy" (Access and SQLite), with the diff preview (§4.5).
- Desktop stores the project encrypted at rest (v0.3); in the browser the v0.3 notice about unencrypted local
  storage is shown before importing identifiable data.

### 7.2 Program editor and dialogs

- The Analysis workspace gains a program editor beside the output log: syntax highlighting, line numbers,
  register-driven warnings on unsupported commands, run all / run selection, open and save programs.
- Each cleaning command gets a dialog; dialogs (and the v1.0 FREQ, TABLES and MEANS dialogs) write their
  command into the editor and run it, as Epi Info's dialogs did.
- A working-view bar shows the source version, the number of recipe steps, record count after SELECT, and
  "Save as new version"; the recipe is listed and individual steps can be undone from the end.
- The data view shows value labels (toggle: labels or codes), and linked datasets.

### 7.3 Migration report screen

The report from §6.2, per project, with download. The command register is a public route like `/validation`.

## 8. Validation and references

### 8.1 Epi Info 7 reference corpus II

The Windows CI route from v0.1 (`fixtures/ei7`, real Epi Info 7 7.2.7.0 reading `.mdb` tables directly) runs
new reference programs over the bundled sample projects: every v1.1 command and the main expression
functions, each followed by FREQ, TABLES, MEANS and LIST output that pins the result. The parser extracts the
numbers and listed rows into fixtures. Epi Info 3.5.x tables are read by the same route (Epi Info 7 reads them
as Access tables); where Epi Info 7's upgrade of an Epi Info 3 project can run headless, it is a second check
on the mapper (Task 3 finds out; if it cannot, that is recorded, not worked around).

Epi Info 7 in CI cannot open `.prj` views (v0.1 spike), so reference programs READ `.mdb` tables and use
table-level RELATE and MERGE with explicit keys; that pins the one-to-many semantics (which level FREQ counts
at after RELATE). View-level behaviour (RECSTATUS exclusion, code-table labels, Mirror fields, page joins,
child-view links) is pinned by the golden imports (§8.2). Task 3 may also probe a source-built Epi Info 7 with
a `.prj` it writes itself; that is optional and never blocks the task.

### 8.2 Golden imports

For each sample project, a golden fixture records every dataset's schema, labels, links, row count and content
hash. It is produced independently of the mapper: native `mdb-export` (or SQLite) dumps plus a small script
following the Epi Info 7 layout, reviewed by the owner. SQLite and SQL Server copies of each Access sample are made by a
copy script that moves the tables verbatim (names, types, rows; no mapping), so cross-back-end equality tests
the readers and the mapper, not the script. SQL Server runs in CI in the SQL Server Developer edition
container and must reproduce the Access hashes.

Epi Info 3.5.4 samples (D12): committed with a `NOTICE` if redistributable; otherwise CI downloads them from a
pinned URL with a SHA-256 check and never commits them; if neither works, Epi Info 3.5.x support ships labelled
"unvalidated" in the app and the report, its criterion-2 rows are dropped, and that is an owner review at
Task 2.

### 8.3 R export

Results on a working view export the materialised working-view data as CSV plus the v1.0 procedure script;
the recipe is included as Epi Info commands in comments. CI runs the scripts as in v1.0. Translating recipes
into R code is not in v1.1 (it would need its own verification route); revisit with the v1.2 MCP server and
CLI.

## 9. CI, budgets and testing

- `engine.yml`: `epiora-mdb`, `epiora-legacy`, `expr`, `manage`, `pgm` tests; parity over the extended
  corpus; new fuzz targets `mdb_any` (arbitrary bytes into the reader), `legacy_meta_any` (arbitrary meta
  tables), `pgm_any` (arbitrary program text), `recipe_any` (random command sequences: re-run reproduces the
  working-view hash).
- `legacy.yml` (new): golden imports from Access and SQLite; SQL Server container job; Epi Info 3.5.x samples;
  re-import of a modified copy (added, changed, deleted records; an added field) against an expected diff.
- `fixtures.yml`: unchanged rule; the EI7 workflow runs the new reference programs.
- `app.yml`: legacy import, program editor, dialogs and migration report in Playwright on three engines with
  axe; offline import in the browser.
- **Budgets:** core engine wasm ≤ 409,600 bytes gzip -9 (E3, unchanged; about 362 KB used at v1.0). `expr`,
  `manage` and `pgm` ship as a second, lazily loaded wasm module (loaded on first use of the editor, a cleaning
  dialog or a working view), with the same native/wasm parity rule; its size is reported and gets an
  owner-chosen budget at Task 18; any change to E3 is an owner decision; first load < 5 MB; the mdb wasm module loads only on the import screen and its size
  is reported, not gated. New `legacy_import_large`: import of a synthetic Epi Info 7 project (size proposed by
  Task 18) — Task 18 measures 10 runs and proposes a threshold; the owner picks it; Task 19 gates it.
- **Validation report** `docs/validation/v1.1.md`, generated by CI: every statistic and command with
  references, class and worst error; golden-import results; R-export results; gates; adviser sign-off pending.

## 10. Error handling

New `ImportError` codes: `mdb_truncated`, `mdb_corrupt`, `mdb_password_protected`, `mdb_unsupported_version`,
`legacy_layout_unknown` (not an Epi Info project; offer plain table import instead), `legacy_view_broken`
(one view fails; the others still import and the report says why), `sqlserver_connect`, `sqlserver_auth`.
New `EngineError` codes: `pgm_syntax` (line and column), `expr_type`, `unknown_variable`, `merge_key_type`,
`relate_no_link`, `recipe_replay_mismatch` (never expected; a bug signal). A program syntax error shows the
line in the editor; nothing runs until it parses.

## 14. Risks

| Risk | Mitigation |
|---|---|
| The Epi Info 3.5.x layout differs from what the upgrade code implies | Task 3 probes a headless upgrade as a second check; failing views import as plain tables with a report entry rather than blocking the project |
| Real user projects have layouts the samples don't | `legacy_layout_unknown` and per-view isolation; the report says exactly what failed; widen the samples at the v1.6 pilot |
| Data-management semantics silently differ from Epi Info 7 | Reference programs for every command; method choices are owner reviews, not code comments |
| Engine size grows past the budget with the interpreter | Split into a lazily loaded module before touching the budget |
| Working-view results that can't be reproduced | Recipe replay is fuzzed and hashed; `recipe_replay_mismatch` fails CI |

## 15. Review focus (for the plan)

1. **A legacy field imported with a changed meaning and no report entry.** Expect every field and record to
   be accounted for in the report, and golden fixtures produced independently of the mapper. → Tasks 4, 7, 8.
2. **A cleaning command that differs from Epi Info 7 in an edge case** (missing values, RECODE boundaries,
   MERGE duplicates). Expect reference programs to pin each case and Task 14 to record the choices. → Tasks
   3, 11, 14.
3. **A `.pgm` that silently skips work.** Expect every unsupported command reported with its line and every
   later affected result marked. → Task 12.
4. **A result on a working view that can't be reproduced from its receipt.** Expect recipe replay to
   reproduce the working-view hash, fuzzed. → Tasks 11, 13.
5. **Hidden clock reads.** Expect `SYSTEMDATE` to come only from the recipe's as-of value. → Tasks 10, 11.
6. **Thresholds, fixtures and hash rules from prose.** Expect golden imports, the register and the
   `legacy_import_large` threshold only from owner-reviewed tasks. → Tasks 1, 4, 6, 18.
7. **SQL Server credentials or connection strings stored or logged.** Expect them held in memory for the
   import only, never in the store, settings or logs. → Task 9.
8. **A re-import that duplicates or drops records.** Expect the diff keyed on `GlobalRecordId`/`UniqueKey`, an
   unchanged file creating nothing, and the modified-copy fixture matching its expected diff. → Tasks 7, 15.
